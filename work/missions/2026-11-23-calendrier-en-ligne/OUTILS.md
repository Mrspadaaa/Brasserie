# Outils de test du Calendrier — état de l'art et décision (23.11)

## État de l'art
- Problème d'école : test de bout en bout d'une app web mobile (gestes tactiles, rendu, accessibilité). Méthode standard : un lanceur E2E maintenu, pas des scripts puppeteer faits main (L29 ; « outils type playwright, api testing »).
- Examiné : **Playwright Test** (Microsoft, 1.65) : projets d'appareils (Pixel 7 : `isMobile`, `hasTouch`), localisateurs par rôle et texte à attente automatique, `expect` web-first et `expect.poll`, `test.step`, trace à la reprise, vidéo et capture à l'échec, `toHaveScreenshot` comparé au pixel, reprises, parallélisme, rapport HTML, `webServer`, horloge simulée (`page.clock`), fixture `request` pour l'API. Cypress (pas de vrai tactile multi-points, un seul onglet) et WebdriverIO (plus lourd, même CDP dessous) écartés. Puppeteer seul : pas de lanceur, ni attente, ni rapport.
- Gestes : `locator.tap()` / `page.touchscreen` pour le toucher ; pour glisser minuté, doigt tenu immobile, tremblement ±1 px et appui long, CDP `Input.dispatchTouchEvent` (session `newCDPSession`) : seule voie qui règle le temps entre événements.
- Accessibilité : **@axe-core/playwright** (Deque, 4.14), règles WCAG 2 A/AA.
- Données : build de test (`scripts/parcours/vite.parcours.config.mjs`, `?dev-local&finance-demo=parcours-calendrier`) servi par `vite preview`, fixture `scripts/parcours/fixtures/calendrier.mjs` (+ le passé et « ZZ TEST Geste » de geste.mjs), jamais seedData.ts. App en ligne : lecture seule par `chromium.connectOverCDP('http://127.0.0.1:9222')` sur son Chrome connecté, sans jamais le fermer (`browser.close()` interdit : on ferme seulement son onglet).

## Décision
